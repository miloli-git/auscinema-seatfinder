# Research brief: the typical UX/UI design process (so a solo builder can iterate correctly)

You are a senior product designer / design educator. Do live web research (use web_search) and return
a practical, well-cited PLAYBOOK. The reader wants to LEARN the process and run it himself, correctly,
rather than jumping straight to high-fidelity mocks.

## Who this is for
A strong backend / AI-agent builder (not a trained designer) building a public side project
("AusCinema Seat Finder" - find the cinema seat actually worth sitting in, then hand off to official
booking). He has been jumping straight to polished single-file HTML mocks. He now wants to understand
the real end-to-end UX/UI design process so he can iterate properly on the next phase. He is a solo
builder with no design team and limited time, so the playbook must be realistic for one person, not a
20-person studio.

He is also about to act on a specific reframe he came up with: the product should be MOVIE-FORWARD
(start from "I want to see this film, well") rather than cinema-forward or time-forward, and should
"solve the actual problem" rather than present a ranked-list solution the user has to wrap around
their own needs. Use the seat-finder as the running example where helpful.

## What to research and answer
1. **The canonical design processes** - explain and compare the main frameworks (e.g. Design Thinking
   5 stages, the Double Diamond / Discover-Define-Develop-Deliver, lean UX, Google design sprint,
   typical product-design "discovery -> delivery" pipeline). Cite authoritative sources (IDEO, Nielsen
   Norman Group, IDF, GV, Design Council).
2. **A concrete stage-by-stage workflow** a SOLO builder can actually follow, from problem to shipped
   UI. For each stage: the goal, the key activities, the artifacts produced (e.g. problem statement,
   user/JTBD, user flows, IA, wireframes, lo-fi -> hi-fi, design system, prototype, usability test),
   and a realistic "minimum viable version" of that stage for one person.
3. **How to iterate correctly** - lo-fi before hi-fi, divergence then convergence, when to test, how
   to avoid solution-first thinking, how many iterations, how to know a direction is "done enough".
   Practical, not theoretical.
4. **Lightweight user research / validation** a solo builder can do cheaply (interviews, JTBD,
   guerrilla testing, analytics, the "5 users" rule) - and what to skip.
5. **Tooling** - what tools fit each stage for a solo builder (Figma, FigJam, whiteboard, Maze, etc.),
   and where AI tools fit in.
6. **Applied to the seat-finder**: sketch how the next phase SHOULD run through the process given his
   "movie-forward, solve-the-actual-problem" reframe - problem framing, JTBD, flows, then UI - so he
   sees the process on his own example.

## Output format (write to stdout as markdown)
- **BLUF** (3-5 bullets): the process in one breath + the single biggest mistake to avoid.
- **The frameworks** (short compare table + which to actually use).
- **Solo-builder workflow** (the stage-by-stage playbook with artifacts + minimum-viable version).
- **How to iterate** (the loop, divergence/convergence, when to test).
- **Applied to the seat-finder** (concrete walkthrough of the next phase).
- **Tooling** (per stage).
- **Sources** (links).
Concrete and actionable. No filler. No em dashes.
